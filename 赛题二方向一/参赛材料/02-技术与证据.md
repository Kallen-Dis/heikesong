# 技术、正确性与证据

## 1. 结构

```mermaid
flowchart LR
    Goal[业务目标 / 数据Agent] --> Plan[可选LLM提出可见草案]
    Goal --> Align[有限规则对齐]
    Plan --> Align
    Ontology[本体与指标定义] --> Align
    Align --> Clarify[明确口径 / 实体 / 时间]
    Clarify --> Contract[预览语义契约]
    Contract --> Gate[版本 / 服务端范围 / 关系粒度]
    Gate --> Compiler[重新编译参数化SQL]
    Compiler --> Warehouse[现有数仓 · 当前DuckDB]
    Warehouse --> Evidence[完整结果与执行证据]
    Evidence --> Replay[同环境重放]
    Evidence --> Compare[场景级共同支持与权重]
    Compare --> Scenario[显式假设下的方案比较]
```

`preview` 会检查关系与 `EXPLAIN`，不会运行目标结果查询。它仍会读取本地数据进行版本和质量检查，不能说预览完全不访问数据库。

当前分层比较组件接受结构化计数，与账本查询入口是不同组件。离线反例用于证明使用条件的必要性；尚未把任何查询结果都自动转换成通用比较合同。

## 3. 两阶段契约

`semantica.contract/v1` 包含：

```text
plan        原始问题/metric/variant/filters/ranking/threshold/time
meaning     指标定义/表达式/单位/粒度/时间字段/操作类型
revisions   语义内容版本/实际数据内容检测标识/数据截止日
policy      服务端允许区域/聚合访问/结果行数上限
query       SQL模板/独立绑定参数
lineage     编译产物使用的表
disclosure  可读口径与筛选
limitations 当前边界
contract_id 契约内容SHA-256校验值
```

执行步骤：校验内容一致性 → 核对当前版本 → 重建受支持的 Alignment → 应用服务端范围 → 编译 → 对照契约 → 执行 → 完整证据。

客户端传来的SQL不会直接执行；编译器从受支持的计划重新生成SQL。内容哈希不是授权凭据，服务端策略检查必须独立成立。当前MCP服务默认全区域聚合，企业身份尚未接入。

## 4. 证据与重放

`semantica.evidence/v1` 保存契约、完整结果表、时间、澄清方式与信任元数据。证据校验失败则拒绝重放；数据或语义变化则旧契约失效；同环境运行后比较所有行列。

仓库版本来自实际连接的表结构、行数与DuckDB行哈希之和，适用于内存库及当前本地库的变更检测。它不是原始数据的加密承诺，也不保证跨DuckDB版本稳定。

语义版本来自YAML内容。缓存不再仅依赖固定的默认库路径；返回值深复制，调用方改动嵌套表格或证据不会污染缓存。

当前检测需要扫描本地表；在真实大数据系统中应改为可信快照ID、提交版本或数据产品发布版本，不将原型性能外推到企业规模。

## 5. 使用条件的准确数学含义

观察总体率：`r(c) = Σ delayed(c,g) / Σ delivered(c,g)`。

声明共同构成后的描述性率：`r*(c) = Σ w(g) × delayed(c,g) / delivered(c,g)`，其中 `w(g)≥0` 且 `Σw(g)=1`。

二者回答不同问题。公共权重必须对应一个声明的目标构成或描述性比较目的。组件检查：

- 恰好两个承运商、至少两个共同区域。
- 每个承运商-区域唯一，计数为合法整数，`0≤delayed≤delivered`。
- 共同支持完整，每组分母为正。
- 权重恰好覆盖区域集合，有限非负且总和为1。
- 未提供权重时仅展示观察，等待声明。

标准化不消除所有混杂，组件始终不批准“因此实际更换承运商将改善”的因果建议。

## 6. 情景模型

历史队列的已妥投率来自实际查询；成本、覆盖和效力由用户给定，不能从账本中推断。

```text
目标覆盖量 = floor(已妥投数量 × 声明覆盖率)
实际覆盖量 = min(目标覆盖量, floor(剩余预算 / 单票成本))
期望避免超时 = Σ 实际覆盖量 × 历史超时率 × 声明相对效力
估算支出 = Σ 实际覆盖量 × 声明单票成本
每避免一次超时的盈亏平衡价值 = 估算支出 / 期望避免超时
```

同成本、同效力的线性模型中，按单票期望收益分配预算。小样本默认不自动纳入干预；敏感性使用效力×0.8/1.0/1.2并限制在0..1。

不能用总超时量代替预算收益排序：1000票/50超时与100票/40超时，预算只能覆盖100票时，第二组的单票潜在收益更高。

假设包括：未来存在相同规模和历史率的可比队列、组内随机覆盖、效力是相对风险降低。它们尚未实测，结果是条件模拟而非预测。未完成运单单独披露，未来签收日期按截止日截尾。

## 7. 本次语义修复

| 原问题 | 修复 |
|---|---|
| 增长问题被回答成一个总量 | 不支持的增长、复合时间等保守拒答 |
| 渠道筛选丢失 | 解析实际数据中的渠道值并参数绑定 |
| 超时率排名变成超时数量排名 | 尊重指标及显式variant，多口径排名澄清 |
| 订单按承运商过滤时缺关联 | 补齐shipment JOIN并披露统计仅含关联运单 |
| 多运单或孤儿关系静默改变聚合 | 当前关联合同违反时阻断 |
| 缺失澄清默认首项、非法选择截断 | 必须明确选择全部点，严格范围校验 |
| 缺日期偷换最近30天 | 类型化入口返回时间澄清 |
| 多行结果只判第一格 | 所有行、列和单元格比较 |
| 整点边界数冒充真实耗时 | `epoch(delivery_time-ship_time)/3600.0` |
| 规则匹配被称为高置信度 | 改为规则校验状态，不冒充统计概率 |

## 8. 评测解释

AmbiQuery-120 为自建回归集。真实耗时修订影响v1十题：A03、A09、A13、A19、C12、D17、E04、E11、E12、E19；seed两题A03/E04。计数变化为380→386、1650→1664、241→243、84→88。平均小时的变化由更准确的时间函数产生，不是增补关键词拟合答案。

独立作者新增24条业务反例，首次19/24，暴露金额阈值、Top3、未知品牌、完成状态、按天趋势五类漏条件。修复策略是拒绝当前无法表达的请求，第二次24/24。首次记录保留在 `eval/adversarial_v2.json`。

应同时看可回答覆盖、有答案正确率和应阻断却执行率，不把拒答问题排除后仅宣传满分。这套反例参与了开发修复，不是严格保留集。

本轮按用户要求控制验证规模，复用定点检查；页面与协议的完整运行情况以实际验收记录为准，不将源码检查当成实际界面成功。
