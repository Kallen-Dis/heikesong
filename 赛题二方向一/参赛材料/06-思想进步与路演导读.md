# 思想进步与路演导读

这份导读帮助你第一次认真理解语枢，并把它讲清楚。先读前六节，再按第七节排练。正式作品介绍见[项目 README](../README.md)，字段与实现依据集中在[技术与证据附录](02-技术与证据.md)。

## 1. 用一分钟理解核心想法

语枢要解决的不是“AI 会不会写 SQL”这一件事，而是：**AI 拿到一个正确的数字后，是否知道这个数是什么意思，以及它能支持什么结论。**

可以把一次数据回答想成一张有说明的收据：上面有结果，也写着统计对象、分母、日期、计算来路和适用条件。没有这些说明，AI 很容易把“账面超时率更高”写成“应该换掉这家承运商”。语枢先让人确认含义，再执行并留下证据，最后在有限比较场景中提醒哪些推断还缺条件。核心命题就是：**算对，不等于用对。**

## 2. 这一版主要进步在哪里

相比“自然语言 → SQL → 返回数字”的问数思路，这一版把注意力推进了三步。

第一步是**语义契约**：先约定这次究竟在算什么。“超时率”是超时票数除以已签收票数，还是除以全部运单？“8月”按哪个日期字段统计？问题含糊时先让用户选，再把指标、时间、筛选和粒度写成可见的执行约定。契约可以理解成“双方先确认好的统计说明”。

第二步是**执行证据**：不仅给一个数，还交代来源、参数、完整结果和版本。确认执行时会检查当前数据、语义定义和范围，并从受支持计划重新编译查询。旧约定遇到版本变化会失效；证据可在相同环境重放。这解决“后来能不能核对这次计算”，不保证原始业务数据本身真实。

第三步是**使用条件**：即使意义和计算都正确，比较也可能不公平。平台在承运商比较中检查两家是否都覆盖目标区域、各区域有没有有效分母、采用哪一套公共权重；在情景模拟中明确成本、覆盖和效力来自用户假设。这里开始关注数字进入报告和建议后的责任。

这三层不是三种新算法。语义层、本体、参数化查询、版本检查和分层比较都有成熟基础。项目的贡献是围绕 Agent 使用数据的过程，把它们组织成可确认、可执行、可核对的接口，并用一个容易复现的反例说明为什么还需要使用条件。

## 3. 把四行例子真正想明白

下表是离线演示台全部业务计数，均为合成。“超时”是已妥投运单中的超时，分母固定为已妥投票数。

| 承运商 | 区域 | 已妥投 | 超时 | 区域超时率 |
|---|---|---:|---:|---:|
| A | 华东 | 900 | 18 | 2% |
| A | 华南 | 100 | 10 | 10% |
| B | 华东 | 100 | 1 | 1% |
| B | 华南 | 900 | 81 | 9% |

总体 A 是 `(18+10)/(900+100)=2.8%`，B 是 `(1+81)/(100+900)=8.2%`。它描述两家公司在**各自现实业务构成下**的已妥投超时情况。A 有 90% 的票在较低风险的华东；B 有 90% 的票在较高风险的华南。直接比较总体率，既混入了区域表现，也混入了业务构成。

拆到同一区域，华东 A=2%、B=1%，华南 A=10%、B=9%。A 每区都高 1 个百分点。“总体 A 更低”和“每区 A 更高”同时成立，算术没有矛盾，是比较问题不同。

如果我们明确问“在相同的华东 50%、华南 50% 构成下，两家历史区域率如何比较”，就用同一套权重：A=`0.5×2%+0.5×10%=6%`，B=`0.5×1%+0.5×9%=5%`。这个排序相对原总体反转，但没有改任何原始计数。

**滑块不会让共同权重下的 A、B 再反转。**设华东权重为 w，A=`10%−8%×w`，B=`9%−8%×w`，二者始终差 1 个百分点。华东 80% 时 A=3.6%、B=2.6%；纯华南时 10%/9%，纯华东时 2%/1%。拖动是展示“比较条件会改变数值”，不能说“找到某个滑块位置就让 A 更好”。

共同权重仍只是**描述性比较**：按一个声明的构成整理已有记录。它没有充分控制路线、货物、客户和时间，也没有真正更换后的干预数据。因此不能继续推出“换成 B 一定减少多少超时”。任务可以继续，但下一步需要真实效果证据，或明确声明假设后仅做条件模拟。

## 4. 两种演示材料分别证明什么

| 材料 | 用途 | 数据与执行 | 可诚实声称的范围 |
|---|---|---|---|
| `演示台.html` | 一眼看懂算对与用对的差别 | 上述四行合成计数；本地 JavaScript | 数学反例可复算；导出 JSON 是结构示意 |
| Streamlit「契约与证据」 | 看真实原型怎样确认与执行一次查询 | 生成的合成物流账本；DuckDB 查询 | 澄清、预览、人工确认、执行与同环境证据重放 |

这里“真实执行”指程序确实对演示数据库运行查询，数据依然是合成的。两种材料不是同一次调用：不能拿离线 JSON 说成 MCP 回执，也不能把账本查询的结果说成必然就是 2.8%、8.2%、6%、5%。当前尚未把任意账本结果自动接入统一的比较与决策证据链。

Streamlit 中的可选 LLM 只提出草案。人需要核对原问题和草案，选择口径并确认契约；执行由确定性逻辑完成。本版没有展示“模型收到工具反馈、自动修正计划、再次执行”的自主闭环。路演不打开模型按钮，也不把规则运行讲成现场模型推理。

## 5. 用日常语言回答赛题三问

**AI 需要什么形式的数据，如何使用？**需要有说明的结果，而非裸数字。查询前给目录和执行约定，查询后给结果、口径、版本、来路与限制。人可通过页面确认，Agent 可通过 MCP 工具交换结构化内容。AI 负责提出任务与消费结果，平台负责受约束的计算；含糊含义仍需明确选择。

**本体论是不是答案？**本体像统一的业务词典，告诉双方“客户、运单、超时率”指什么，很有价值。但词典不能修好脏数据，也不会自动让两个对象可比。因此还要执行检查与使用条件，不能把本体当作所有问题的万能答案。

**怎样和传统平台融合？**保留数仓的存储和计算，在上面加一层语义与执行接口。先为少量重要指标建立约定，让 BI 和 Agent 共用定义，再接真实身份、可信数据版本及更多仓库。当前已实现 DuckDB；其他平台连接属于后续路线。

## 6. 现在的不足应该怎样讲

当前是有限物流场景原型，语言覆盖和指标范围有限，超出能力的请求会保守拒答。使用条件规则是场景规则，不能自动证明所有业务判断；外部模型也可能忽略返回的限制。当前可保证的是受约束接口的检查，不能保证所有 AI 文本都正确。

数据关系检查采用单订单最多一运单的合同，多运单业务要重新设计粒度。企业身份、可信快照与大数据性能尚未验证；证据重放依赖同数据、同语义、同环境。证据包没有原始数据快照，内容哈希也不是数字签名。下一步价值在于接真实业务与 Agent 轨迹，验证这些条件是否真正减少误用，而非增加一个更大的聊天框。

### 连续讲稿

各位评委好，我们的项目叫语枢，让 AI 取得带使用条件的数据。请先看一个合成物流例子：A 的总体超时率是百分之二点八，B 是百分之八点二。如果只给 AI 这两个数字，很容易写出“应该优先换掉 B”。这不是实际模型运行记录，而是一个我们可以逐项复算的问题：数字算对了，这个建议就充分了吗？

现在把总体拆开。华东，A 是百分之二，B 是百分之一；华南，A 是百分之十，B 是百分之九。两个区域里，A 都更高。请看业务构成：A 的九成票数在低风险区域，B 的九成在高风险区域。总体统计没有骗人，它回答的是两家各自业务构成下发生了什么；但我们想作比较时，已经悄悄问了另一个问题。

所以比较之前，要先说清比较条件。这里声明华东、华南各占一半，用相同权重比较已有区域率，A 就是百分之六，B 是百分之五。我把华东占比调高，两家的数值一起变化，但 A 始终高一个百分点，因为每个区域都是这个差距。这里的反转是相对于原总体排序，不是滑块可以随意制造排名反转。更关键的是，这仍然只描述已有记录，不能证明真的换成 B 就一定改善。路线、货物和时间等因素还没有充分控制。

这就是语枢从普通问数向前推进的地方。第一层，语义契约，先确认“超时率”到底除以已签收运单还是全部运单，统计哪个时间和区域。第二层，执行证据，确认以后再计算，保存来源、参数、完整结果和版本，让这次答案可以核对。第三层，使用条件，告诉 AI 哪些比较成立，哪些行动还缺证据。数字、计算和结论之间，每一步都需要说明。

在我们的 Streamlit 原型里，用户先生成契约，选择口径，核对条件，然后确认执行。程序会检查版本、范围和数据关系，再生成受支持的查询；执行后可以下载完整证据，在相同环境重放。可选大模型只提出草案，仍需人来确认，本版没有模型自动反馈修复的闭环。这里主屏的四行反例用于讲清思想，页面 JSON 也写明是结构示意；另一份合成账本用于验证契约执行。我们不会把两种独立材料说成同一次真实调用。

对于赛题，我们的回答有三点。AI 需要的是附有口径、来路和限制的结果，通过明确接口使用；本体是共同业务词典，还需要执行检查与使用条件；传统数仓继续存储和计算，我们在上面增量增加这层接口。相关技术已有成熟基础，我们的贡献是把它们围绕 AI 使用数据组织起来，并在物流场景做成可演示的原型。我们希望 AI 不只回答“这个数是多少”，还知道“它能说明什么，以及下一步还缺什么证据”。谢谢。

## 9. 五个高频问题

**问：这是不是语义层加 MCP，创新在哪里？**

答：这些基础技术确实已有成熟方案。我们的主张是让接口同时说明“怎么算”和“能怎么用”，并在物流比较中落实共同区域、公共权重及行动条件。辨识度来自这一组合和可复现反例，不宣称发明了本体、MCP 或标准化算法。

**问：到底该选 A 还是 B？标准化后不是 B 更好吗？**

答：在声明的共同构成下，B 的历史描述性率更低，这句话可以说。但采购或更换决定还需路线、价格、服务和真实干预效果。本例不能承诺换 B 会改善多少，也不提供自动更换批准。

**问：AI 在哪里，为什么这么多规则？**

答：系统面向 Agent 提供目录、契约与证据接口，可选 LLM 提出查询草案。规则负责执行检查，人负责确认含义。离线演示没有调用模型，本版也没有自主反馈修复的展示；这条闭环需要后续用真实轨迹验证。

**问：你们保证所有答案正确、证据不可伪造吗？**

答：不作这个保证。当前是合成数据、有限语言和场景，受支持接口能检查特定版本、范围和关系；重放说明本环境结果一致。证据哈希不是签名，也不证明原始数据真实。外部模型是否忠实引用限制仍是待验证问题。

**问：为什么不直接重建一个 AI 数据仓库？**

答：已有数仓擅长存储和计算，我们先把少量重要指标的含义及使用条件变成共用接口。当前用 DuckDB 验证，企业认证、可信快照和其他数仓适配需要逐步接入。这个方向允许增量演进，先解决具体的误用问题。
