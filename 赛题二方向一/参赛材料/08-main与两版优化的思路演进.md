# 从 main 到两版优化：语枢的思想演进

这份文档把三个版本放在一起解释：原 `main` 在解决什么问题，`赛题2-庄子由` 增加了什么，`赛题2-Astra评审优化-庄子由` 又向前推进了哪一步。重点是思想与责任范围的变化；具体路演稿见文末的两份导读。

先记住这条主线：

**main：把用户的业务意思落实到查询。**

**第一版优化：把一次查询变成可确认、可核对的约定，并说明数字的使用条件。**

**第二版优化：条件不满足时，让反馈改变 AI 的下一动作，使任务在原约束内继续。**

原 main 已经是一套有本体、澄清和确定性编译的语义问数系统。后续两版沿用这些基础，并扩大平台需要承担的责任。

## 1. 三版各自最关心什么

| 版本 | 最关心的问题 | 主要交付给使用者的东西 |
|---|---|---|
| 原 main | 用户说的词，能否映射到正确的指标、口径、实体与时间？ | 带统计说明的查询答案 |
| 第一版：语义执行网关 | 这次计算能否事先确认、事后核对？结果足以支持怎样的比较与建议？ | 查询契约、完整执行回执、场景使用条件 |
| 第二版：任务恢复工作台 | 第一次证据不够时，AI 应该补什么、复用什么、何时交回用户？ | 当前任务状态、具体缺口、合法下一动作、持续有效的结论 |

```mermaid
flowchart LR
    M["main：语义问数<br/>理解口径并执行"]
    G["第一版：语义执行网关<br/>确认计算与使用条件"]
    R["第二版：任务恢复工作台<br/>反馈、补证与恢复"]
    M --> G --> R
```

三个版本都回应赛题二 A“AI 使用的大数据平台”。物流是展示数据使用问题的具体场景；我们没有把主题改成完整的物流调度或供应链优化系统。

## 2. 原 main 的完整思路

### 2.1 最初的问题：表结构没有说明业务意思

用户说“8月的金额是多少”，数据库里却可能同时存在订单毛额、实际支付额和剔除取消后的净实付。用户说“苹果”，既可能指商品品牌，也可能指客户名称。用户说“最近”，时间范围没有确定。

单独给 AI 一份表结构，字段都认识了，仍可能选择错误的业务含义。原 main 的核心判断是：**业务知识应沉淀在平台里，成为可以重复使用的定义与执行规则。**

所以 main 已经超出了“让模型自由写 SQL”的思路。仓库中的裸 DDL Text-to-SQL 是实验对照组，并不能用来代表 main 自己。

### 2.2 本体是业务词典，也是编译的依据

原项目把概念、关系和公理写进本体资料，把指标、分母、时间字段及表达式写进指标口径库，再用同义词、业务口语和教学产物连接用户措辞。

例如，“单量”可以对齐到订单数量；“已签收口径”可以明确某种超时率分母。系统将这些信息整理成一个结构化查询计划，再交给编译器。

这里应准确理解“本体”的实际职责：执行链主要依靠指标定义、词表、数据值识别和固定编译规则。关系资料提供业务设计依据，JOIN 由受支持的编译规则装配。当前实现没有对任意本体图进行通用推理。

### 2.3 五步闭环已经能够完成真实查询

原 main 的主链是：

`解析 → 对齐 → 澄清 → 编译 → 披露`

以“8月的金额是多少”为例，可以这样理解：

1. 识别时间和金额指标，形成受支持的查询计划。
2. 发现金额存在多种口径，返回澄清选项。
3. 选择明确口径后，编译为 SQL；筛选值采用参数绑定。
4. 在合成数据库上执行计算。
5. 返回结果，同时披露指标、时间、筛选和信任标签。

支持范围还包括部分排名、阈值及分组查询。未覆盖的库存、毛利等问题会报告不足。核心语义查询链使用有限规则，可以不调用语言模型运行。

这已经具备两个重要思想：含糊的意思需要澄清；返回的数字需要附带统计说明。

### 2.4 main 已有平台维护和 Agent 接口

它还有几项容易被后续版本介绍遮住的能力：

- **本体维护**：用户给新术语和定义，LLM 可生成指标草稿；通过结构、安全与可执行检查后写入词库并热加载。
- **澄清回流**：保存选择样本，统计常用口径和歧义热点，提出维护建议；回流本身不会自动改写本体。
- **语义缓存**：缓存键包含语义版本，本体或数据库文件变化后不再命中旧版本。
- **MCP**：已有指标目录、数据卡片，以及对齐、自然语言查询和指标直查工具，外部 Agent 可以消费这些能力。
- **实验与消融**：用自建题库比较不同输入方式、拆掉组件观察影响，为实现选择提供证据。

因此，main 已经在探索一个完整方向：平台集中维护业务语义，受支持的请求经确定性编译执行，用户和 Agent 共用接口。

### 2.5 main 的边界在哪里

它的主要完成单位仍是**一次受支持的查询**。结果出来后，重点是披露“算了什么、怎么算”。结果是否足以支持公平比较、行动建议，以及缺证后怎样继续，并没有构成贯穿任务的执行过程。

还要区分设计原则与实际默认行为：`QueryLoop.ask` 默认返回澄清，但原 MCP 的 `nl_query` 默认开启自动首项；缺失澄清选择也可能被默认为零号选项。原版有澄清能力，却并非所有入口都强制要求用户确认。

信任标签会显示截止日、行数和空结果，原“高置信度”来自规则对齐与披露，并非统计概率。权限裁剪、成本估算在当时的验证器中仍列为规划。它们不能因出现在模块标题里就被当成已完成能力。

## 3. 第一版相比 main：从语义问数到有条件的数据使用

对应分支：`赛题2-庄子由`。

### 3.1 第一项变化：先确认计算约定，再执行

main 已经能够对齐、澄清和参数化计算。第一版将这些能力组织成更明确的两阶段流程：

`预览契约 → 用户核对 → 确认执行 → 生成完整证据 → 同环境重放`

契约写明指标、口径、粒度、时间、筛选、来源、版本与策略。执行时服务端重新检查、重新编译，不能把客户端传来的 SQL 当成执行依据。

思想上的变化是：**“这次查询是什么意思”成为执行前必须核对的约定。** 原有披露继续保留，同时增加了预览与执行之间的明确责任边界。

澄清也更严格：MCP 默认不代选，用户必须给出完整、合法的选择；实验自动选择会明确标注为未经用户确认。

### 3.2 第二项变化：把计算证据和失效条件做实

main 已有展示 SQL、结构化结果和缓存版本。第一版增加完整回执，将契约、参数、完整结果、版本和来源联系起来，支持在相同环境核对重放。

版本的作用也扩大了：原来主要避免命中旧缓存；现在还要检查“用户预览之后，数据或定义是否变化”，决定原契约是否仍能执行。

运行时新增关系质量检查，发现主键、孤儿关联或不符合单订单至多一运单的粒度要求时阻断计算。原本已有的本体校验检查的是定义和表达式，这些检查进一步覆盖当前账本的实际关系。

这项进步将“我给你统计说明”推进到**“你可以核对这次执行，并知道原约定什么时候失效”**。哈希仍只用于一致性检查，不证明现实数据真实，也不替代签名或身份认证。

### 3.3 第三项变化：结果正确之后，还要检查怎么使用

第一版最重要的新提问是：**同一个数字进入比较与建议之后，又增加了哪些成立条件？**

它用一个独立合成例子说明问题：

| 承运商 | 华东超时率 | 华南超时率 | 两区各自票量构成 | 总体超时率 |
|---|---:|---:|---|---:|
| A | 2% | 10% | 华东90%、华南10% | 2.8% |
| B | 1% | 9% | 华东10%、华南90% | 8.2% |

总体看 A 较低；拆到同一区域，B 两区都较低。两种计算都正确，只是比较问题不同。采用共同的华东50%、华南50%，A=6%、B=5%。

于是平台责任从正确执行指标，扩展到物流比较中的共同支持、明确权重与假设。决策实验室进一步将历史观察、用户声明的效力及成本、公式算出的情景结果分开。

共同权重给出的是历史描述性比较；实际更换承运商是否改善，还需要干预、混杂与成本证据。

### 3.4 第一版仍未连接起来的部分

这一版的数学反例、账本契约与条件实验室是分别成立的材料，没有把所有输出串成同一份任务证据。可选 LLM 提出查询草案，用户核对后执行；它尚未展示模型接收工具反馈、补证并恢复任务的闭环。

这也解释了第二版的起点：条件检查已经有价值，但需要让它真正改变下一步执行。

## 4. 第二版相比前两版：从条件检查到任务恢复

对应分支：`赛题2-Astra评审优化-庄子由`。

### 4.1 完成单位变成一项带约束的任务

用户声明：“按已妥投口径、同一发货时间窗，覆盖所有正权重区域，比较 A 与 B。”

此时一次 SQL 成功，只能说明取到一份证据。整个任务是否完成，要看口径、覆盖和版本是否满足，以及比较是否已经计算。系统持续保留任务条件、证据、反馈、下一动作和结论状态。

这版的主链是：

`任务条件 → 既有证据 → 具体冲突或缺口 → 模型选择下一工具 → 实际查询或重算 → 再检查 → 结论`

AI 消费的能力因此增加了一层：除了查询结果，还有当前不满足的要求，以及服务器允许采取的下一动作。

### 4.2 错误具体指向该补哪份证据

两份既有产品分别默认使用已妥投和全部运单分母。它们确实执行查询，但 B 的口径不满足当前任务。平台反馈具体到分母字段，模型选择按正确口径重新取证，再继续计算。

若只缺 B 华南，就补该缺片。若主视图缺失且有备用权限，可用同仓、同窗、同口径的备用视图；若没有合法取证路径，就请求用户处理。

这个过程保留原任务要求。缺失值不能填零，缺区域不能静默删除，模型不能为了得到答案擅自缩小范围。用户显式授权改范围后，结论必须标明新目标，不能称原全域问题已经完成。

这里的最初冲突来自既有产品，不是模型曾经犯错的记录。真实模型承担的是读取反馈、提议下一工具。

### 4.3 证据能复用，结论也能撤销

改变权重不会改变区域计数，所以可以保留取证结果，仅重新计算比较。数据变化则会撤销当前快照的旧证据与结论，之后重新取证。

第二版换了一组用于展示目标变化的合成数据：A 华东2%、华南12%；B 华东4%、华南8%。共同华东权重20%时，A=10%、B=7.2%；改为80%时，A=4%、B=4.8%，较低的一方从 B 变为 A。

两版例子的含义不同。第一版 A 每区都高1个百分点，共同权重下拖滑块不会再次反转；第二版两家各有优势区域，改变共同目标权重可以反转。它们不能混用。

### 4.4 AI 的职责从旁路能力进入恢复过程

main 的核心问数链可离线运行，LLM 主要用于实验对照和教学草稿。第一版增加可见查询草案。第二版让真实模型在反馈之后提出下一动作，再由服务器校验并执行。

计算、工具参数、授权和有限结论类型仍由确定性程序控制。模型不能提交任意 SQL、自编数值或替用户授权。结论由服务器从有效证据构造。

同样叫“闭环”，三个版本含义不同：main 有查询闭环和语义维护回流；第一版有契约与证据流程；第二版增加了**一次任务中的反馈与执行恢复**。

### 4.5 连通的范围仍是有限原型

工作台复用已有编译器，但使用独立的小型内存合成账本和新的任务证据句柄。它还没有把所有旧查询回执自动接入通用恢复层。

任务由结构控件定义；文字目标供人核对。提示中已有合法修复知识。真实记录支持模型在三个有限场景选择动作，并不证明它能独立发现任意修复策略或跨行业泛化。权重复用已做离线核对，未另采真实模型的权重扰动行为。

备用视图来自同仓；变化检测针对整个快照；历史比较仍不能证明更换后的因果收益。这些边界与任务恢复机制一起构成当前作品的准确范围。

## 5. 把思想变化放在一张表里

| 比较项 | 原 main | 第一版：语义执行网关 | 第二版：任务恢复工作台 |
|---|---|---|---|
| 核心问题 | 如何理解并执行业务查询 | 如何确认计算、核对证据与正确使用结果 | 条件失败后怎样继续完成任务 |
| 本体职责 | 业务词典、指标口径及编译依据 | 延续定义，并写入执行契约 | 延续语义底座，任务反馈承担恢复职责 |
| 歧义处理 | 已有澄清；部分入口默认自动首项 | 默认不代选，严格检查完整选择 | 任务结构明确；缺证或授权问题交回用户 |
| 数据检查 | 定义、表达式与可执行性检查，截止日/空结果标签 | 增加实际账本关系质量阻断 | 检查任务证据的口径、覆盖和有效性 |

| 版本作用 | 缓存失效 | 检查预览、执行及重放条件 | 撤销证据与当前结论，恢复后重算 |
| 失败之后 | 澄清、不足或执行错误；外部使用者继续处理 | 阻断无效执行，核对或改问条件 | 模型选择补证、重算、澄清或停止 |
| 模型作用 | 实验对照、指标教学草稿 | 另可提出查询草案，人核对 | 读取实际反馈并提议下一工具 |
| 演示重点 | 问数、教学、实验与战绩 | 正确数字仍需使用条件的逻辑反例 | 同一工作台内的实际反馈和恢复 |

## 6. 哪些改进是已有基础的增强

公平比较，需要保留原 main 的贡献：

- 参数绑定、澄清、MCP、信任元数据、本体校验、教学热加载和版本缓存，原来已经存在。
- 第一版将这些基础推进到显式契约、完整回执、运行时质量阻断和场景使用条件。
- 第二版把检查反馈接入下一动作，增加局部补证、证据复用、结论撤销与人类授权边界。

因此可以将整个方向概括为：**语义问数 → 有条件的数据使用 → 保留用户约束的任务恢复。** 本体继续负责共同业务含义，执行检查与恢复机制逐步补齐它不能单独完成的部分。

展示证据也随目标变化。main 的自建题库和消融说明特定实现的覆盖与组件作用；第一版的数学反例说明“计算正确”与“比较成立”的区别；第二版的真实轨迹说明模型选择如何进入受约束执行。它们回答不同问题，不能拼成一个跨版本的“总正确率”。

原 main 的120题自检、23题可自动判定的模型对照，以及后续概念评审分也不在同一量表上。本文不据此给三版排分，或宣称本体放入提示词在所有模型与场景都无效。

## 7. 怎样用一分钟向别人解释演进

> 原来的 main 已经做了很扎实的语义问数：把业务词汇和指标口径放在平台里，含糊时澄清，明确后编译执行，再披露统计说明。
>
> 第一次优化继续追问：这个数算对以后，能不能支持我们要作的比较？所以增加执行契约与完整证据，用区域构成反例说明结果还需要使用条件。
>
> 第二次优化把这些条件接入下一步执行。口径冲突就重取同口径证据，缺区域就局部补证，无权限就请用户处理；条件或数据变化会撤销旧结论。模型提出动作，平台计算和检查。
>
> 三版共同探索的是：数据平台怎样让 AI 理解数据、正确使用数据，并在当前证据不足时继续做事。当前成果仍限于合成物流原型。
